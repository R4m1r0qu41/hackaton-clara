Plan de build de Crédito Claro

El trabajo ocurre en Julio-Cuellar/cuentasClaras, por pull requests, con cuatro personas en dos equipos de dos. El repo ya tiene el motor: extracción, cálculo, semáforo, SIPRES, Banxico y respuesta con verificador. El plan agrega un servidor pequeño en Node.js, la página, el mapa y un cambio de dos nodos en n8n.

Resumen

Se reutiliza el motor

No se reescribe nada. El servidor hace require de los módulos que ya tienen pruebas. Todo el repo es CommonJS y el servidor también.

n8n cambia solo dos nodos

Los nodos Code "Procesar" y "Elegir respuesta" pasan a HTTP Request hacia el servidor. El resto del flujo de GUIA-N8N.md sigue igual, y el flujo actual queda como respaldo.

La página usa el mismo motor

/api/consulta corre la misma cadena en el servidor, así que la página no depende de n8n.

Sin base de datos

Dos archivos JSON capturados a mano en datos/procesado/. Python no entra: el repo es Node.js de punta a punta.

Entrada de P0: una persona pega el texto de una oferta o etiqueta; el modelo lo extrae y procesar() calcula, asigna el semáforo y verifica la entidad. Además: verificar una entidad por nombre, la página y el mapa. La selección guiada por productos reales queda como P1.

Este plan sustituye a las versiones anteriores del artefacto. La documentación de credito_claro (por ejemplo plan-equipo.md y scope-equipo.md) quedó desactualizada.

GET/api/salud · errores

{ "ok": true, "ia": false, "datos_al": "30/10/2026" }   // ia: hay clave de OpenRouter configurada

{ "error": { "codigo": "entrada_invalida", "mensaje": "Falta el campo texto." } }
// 400 entrada inválida · 401 clave del bot (X-Bot-Key) · 500 error propio
// Una falla del modelo NO es un error: responde 200 con origen "plantilla".

Los endpoints de n8n llevan una clave compartida en la cabecera X-Bot-Key, guardada como credencial de n8n y como variable de entorno del servidor, porque quedan expuestos por un túnel si n8n es remoto.

Cambio en n8n

Se parte del flujo de n8n/GUIA-N8N.md. Solo cambian dos nodos y se agrega una rama.

Reglas de PR

Propuesta para confirmar con Julio. Los nombres de las personas y la pareja de cada equipo los define JR.

  • Una rama por tarea, con prefijo del equipo: eq1/servidor-base, eq2/n8n-respaldo. PR pequeño hacia main; nada de commits directos a main.
  • La revisión la hace una persona del otro equipo. Se revisa que lo desconocido sea null, que cada dato lleve fuente y fecha, y que no haya claves.
  • node --test en verde antes de pedir revisión.
  • Si un PR cambia un módulo existente, se corre node scripts/empaquetar.js y se incluyen los n8n/nodos/* regenerados, para que el flujo de respaldo siga válido. flujo/empaquetado.test.js debería avisar si faltan (por verificar).
  • Ninguna clave en el repo ni en los JSON exportados de n8n. Las credenciales se crean en n8n y en .env (ya ignorado por .gitignore).
  • Cada PR dice qué cambia, qué prueba lo cubre y qué decide el servidor frente a n8n.

Claude solo lee ese repo. Clonar, crear ramas o abrir PR requiere la autorización de JR.
